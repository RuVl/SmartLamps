# 1. Arduino, а не ESP-IDF

Дата: 2026-09-13
Статус: принято

## Контекст

Прошивке нужны: веб-панель настроек, база настроек, работа с лентой, а в перспективе —
распознавание слова активации через `esp-sr`. ESP-IDF даёт прямой доступ к `esp-sr`,
FreeRTOS, I2S и таблице разделов, и для голосовой части он удобнее.

Одновременно принято решение, что **ESP8266 остаётся полноценной целью сборки**: вторая
лампа пары работает на имеющемся D1 mini и собирается из того же дерева исходников.

## Решение

Arduino на обеих платах.

## Причины

ESP-IDF не поддерживает ESP8266. Для него существует отдельный `ESP8266_RTOS_SDK` —
формально «в стиле IDF», но это другая кодовая база, отставшая на несколько лет, и
Arduino-библиотеки под ней не работают. Выбор ESP-IDF означал бы две разные прошивки в
двух разных фреймворках вместо одного дерева с HAL.

Вся существующая экосистема проекта — GyverLibs Settings, GyverDB, EncButton, FastLED —
это Arduino-библиотеки. Переезд на IDF означает переписать веб-панель с нуля ради
удобства, которое понадобится только на последнем этапе.

`ESP_SR` доступен как библиотека ядра arduino-esp32, то есть голос на Arduino достижим.

## Следствия

Таблица разделов задаётся через `board_build.partitions`, а параметры SDK — через
`sdkconfig`-опции платформы. Это менее гибко, чем в IDF, но достаточно.

**Ограничение, которое из этого следует:** Arduino API не должен просачиваться в ядро.
`core/` и `effects/` не используют `String`, `millis()`, `Serial` и прочий Arduino —
только `hal/`. Если через год IDF всё-таки понадобится, переезжает только HAL, а
эффекты и ядро остаются нетронутыми. Это же условие делает возможными тесты на хосте.
