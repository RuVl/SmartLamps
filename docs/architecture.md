# Архитектура

Одно дерево исходников собирается под две платы. Эффекты, написанные один раз, работают
на обеих и тестируются на компьютере.

## Слои

```
src/
  main.cpp     точка входа, только старт
  app/         сборка системы, задачи, состояние лампы
  hal/         LedDriver, Button, Storage — интерфейс + реализация под плату
    esp32/ esp8266/ sim/
  core/        Matrix, Frame, Param, Effect, Registry, PostFX
  effects/     по файлу на эффект
  net/         WiFi, Mqtt, WebUi, Ota
  audio/       (этап 6+) I2S, FFT, wake word — только ESP32-S3
  sim/         симулятор: та же Lamp на хосте, кадр в браузер по SSE, 2D и 3D-вид
test/test_core/  тесты ядра на хосте
```

**Правило зависимостей.** `core/` и `effects/` не знают ни о сети, ни о базе, ни о
драйвере ленты, ни об Arduino. Зависимости идут в одну сторону: `app → net, hal, core`
и `core → ничего`. Именно это делает эффекты переносимыми между платами и
тестируемыми на компьютере, где нет ни ленты, ни WiFi.

## Конвейер кадра

```
снимок параметров → Effect::render(Frame&, dt) → PostFX → hal::LedDriver::show()
                                                  гамма
                                                  лимит тока
```

Эффект рисует в полную силу и ничего не знает о яркости. `PostFX` применяет
гамма-коррекцию (слайдер в процентах воспринимается нелинейно) и ограничение тока под
блок питания. Драйвер отдаёт кадр в DMA и возвращает управление, не дожидаясь, пока
последний бит уйдёт в ленту.

## Кто где выполняется

На ESP32-S3 два ядра, и это меняет структуру сильнее, чем объём памяти:

| Ядро 0 | Ядро 1 |
|---|---|
| WiFi, MQTT, веб-панель, OTA | рендер кадра |
| кнопка, база настроек | PostFX |
| I2S-микрофон, FFT, wake word | выдача в RMT |

Между ядрами каналы без блокировок: снимок параметров (`std::atomic<int16_t>`,
однословная запись атомарна), два «желания» владельца в `Lamp` (`wantOn_`,
`wantEffect_` — тоже по одному атомарному слову; сеттеры только записывают их, а
`render()` в начале каждого кадра сравнивает с тем, что на матрице, и сам ведёт
переход — состояние перехода принадлежит только рендеру), почтовые ящики
`hal::Mailbox<T>` для кодов отключения WiFi/MQTT из колбэков SDK и кольцевой буфер
спектра. На горячем пути рендера мьютексов нет вообще.

На ESP8266 ядро одно, порядок тот же, всё крутится в кооперативном цикле. Разница
спрятана в `app/`.

## Темп

Лампа рисует с фиксированной частотой около 60 кадров в секунду. Эффект получает `dtMs`
и сам решает, насколько продвинуться, — поэтому скорость анимации одинакова на обеих
платах и не зависит от того, открыта ли веб-панель.

## Смена эффекта

Переход идёт через затухание в чёрный примерно за 300 мс: старый эффект гаснет, новый
разгорается. В памяти при этом живёт один эффект, арена одна.

Настоящий кросс-фейд потребовал бы двух арен, двух буферов кадра и двойного счёта во
время перехода — на ESP8266 это заметно, а выигрыш в красоте небольшой.

## Реестр эффектов

Эффекты регистрируют себя сами: `REGISTER_EFFECT` в конце файла связывает эффект в
список до запуска `main`. Списка, который надо поддерживать руками, не существует.

Активный эффект строится через placement new в статической арене. Слишком большой
эффект не компилируется — см. `docs/adr/0002-static-arena.md`.

## Параметры и хранилище

`Param` — единственное описание настраиваемой величины. Из него выводятся виджет в
панели, ключ в базе (`hash("<эффект>.<параметр>")`), топик MQTT и поле в JSON состояния.

Хранилище — GyverDB поверх LittleFS. Запись отложена: значение меняется в памяти сразу,
во флеш падает, когда десять секунд ничего не двигалось. Это бережёт ресурс флеша при
перетаскивании слайдера и не вносит задержек в кадр.

Лампа поднимается после пропадания питания с тем же эффектом, яркостью и состоянием
вкл/выкл. Сеть для этого не нужна.

## Кнопка

Одна сенсорная площадка (ttp223), четыре жеста. Распознаёт их EncButton в `hal/`, смысл
задаёт `app/Lamp.cpp`:

| Жест | Действие |
|---|---|
| касание | включить / выключить |
| двойное касание | следующий эффект |
| тройное касание | зарезервировано под маячок парной лампе (этап 5) |
| удержание | яркость: каждое новое удержание ведёт в противоположную сторону, 0→100 за ~3 с |

Одиночное касание отдаётся только когда закрылось окно двойного (200 мс): иначе его не
отличить от начала двойного. Это и есть вся задержка реакции; удержание начинается через
300 мс. Предыдущий эффект — из панели или по MQTT.

## Геометрия матрицы

Размеры и ориентация задаются константами сборки, но никаких макросов в выражениях:
`core/Matrix.h` — обычная функция, принимающая геометрию аргументом. При старте
строится таблица на `width × height` записей (512 байт для 16×16), и рендер только
читает из неё.

Отсюда два следствия: все восемь допустимых комбинаций угла и направления проверяются
тестами на хосте в одном бинарнике, а невозможная комбинация отсекается `isValid`, а не
молча подменяется значением по умолчанию.
