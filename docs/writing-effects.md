# Как написать эффект

Эффект — это один файл в `src/effects/`. Больше ничего править не нужно: ни списка
эффектов, ни меню, ни базы настроек, ни топиков MQTT. Всё это выводится из самого файла.

Эталон — `src/effects/Fire.cpp`. Ниже он разобран целиком.

## Скелет

```cpp
#include <FastLED.h>
#include "core/Registry.h"

namespace {

struct MyEffect final : core::Effect {
    core::Param speed{*this, "speed", "Скорость", 1, 100, 40};

    void render(core::Frame& f, uint16_t dtMs) override {
        // рисуем
    }
};

}  // namespace

REGISTER_EFFECT(MyEffect, "Моё имя", ::core::Tag::Ambient)
```

Четыре обязательные вещи: `final : core::Effect`, анонимный namespace,
реализация `render`, строка `REGISTER_EFFECT` в конце.

`REGISTER_EFFECT` принимает тип, отображаемое имя (его увидит пользователь в панели и
им же эффект называется в MQTT) и тег — категорию для группировки списка: `Ambient`,
`Dynamic`, `Reactive`, `System`.

## Параметры

```cpp
//          владелец, ключ,     подпись,     min, max, по умолчанию
core::Param hue{*this, "hue", "Оттенок",      0, 255,  20};
```

Из одного объявления получается:

| что | как выглядит |
|---|---|
| слайдер в веб-панели | подпись «Оттенок», диапазон 0–255 |
| ключ в базе настроек | `hash("Моё имя.hue")` |
| топик MQTT | `lamp/<имя>/cmd/param/hue` |
| поле в JSON состояния | `"hue": 20` |

Порядок объявления — это порядок слайдеров в панели.

Ключи разных эффектов не пересекаются, потому что в хеш входит имя эффекта. Поэтому
параметр можно смело называть `speed` в каждом эффекте — префиксы вроде `fire_speed`
не нужны.

Параметр читается как обычное число:

```cpp
f.fade(uint8_t(speed));
if (hue > 128) { ... }
const uint16_t step = 1000 / (10 + int(speed));
```

Под капотом это `std::atomic<int16_t>`: значение может измениться в любой момент из
веб-панели или по MQTT, пока `render` выполняется на другом ядре. Ничего страшного —
кадр просто нарисуется с новым значением. Но если параметр используется в цикле
несколько раз и важно, чтобы значение было одним и тем же, прочитай его один раз в
локальную переменную.

## Рисование

`Frame` — единственный способ добраться до пикселей:

```cpp
f.width(), f.height()      // размеры матрицы
f.at(x, y) = CRGB::Red;    // пиксель по координатам
f.at(x, y).fadeToBlackBy(8);
f[i]                       // линейный доступ, если геометрия не важна
f.fill(CRGB::Black);
f.fade(20);                // затемнить весь кадр
```

Начало координат — левый нижний пиксель, как его видит зритель. Как это ложится на
реальную ленту — забота `core/Matrix.h`; при сборке второй лампы с другой ориентацией
матрицы эффекты править не придётся.

**Никогда не индексируй ленту напрямую по координатам.** `f.at(x, y)` учитывает тип
матрицы, угол подключения и направление ленты. Выход за границы не портит память:
координаты прижимаются к краю.

## Время

`render` получает `dtMs` — сколько миллисекунд прошло с прошлого кадра. Лампа рисует с
фиксированной частотой около 60 кадров в секунду, но нагрузка бывает разная, и кадр
может задержаться.

**Не считай шаги, считай время.** Плохо:

```cpp
void render(core::Frame& f, uint16_t) override {
    position_++;            // на загруженной лампе анимация замедлится
}
```

Хорошо — накопитель:

```cpp
void render(core::Frame& f, uint16_t dtMs) override {
    const uint16_t stepMs = 1000 / (10 + int(speed));
    accumulator_ += dtMs;
    while (accumulator_ >= stepMs) {
        accumulator_ -= stepMs;
        advance(f);          // один шаг симуляции
    }
    draw(f);
}
```

Так эффект выглядит одинаково на ESP32-S3 и на ESP8266, при открытой веб-панели и при
активном MQTT. Для плавных, не пошаговых анимаций проще домножать скорость на `dtMs`
напрямую.

## Состояние

Поля структуры — это состояние эффекта. Оно живёт, пока эффект активен, и исчезает при
переключении. Если состояние нужно обнулить при запуске — `begin`:

```cpp
void begin(core::Frame& f) override {
    for (uint16_t i = 0; i < f.count(); ++i) heat_[i] = 0;
}
```

**Размер имеет значение.** Эффект строится в статической арене на 768 байт
(`EFFECT_ARENA_SIZE`). Карта тепла у `Fire` — 256 байт, помещается спокойно. Если не
влезешь, сборка не пройдёт с внятной ошибкой:

```
static assertion failed: MyEffect does not fit into EFFECT_ARENA_SIZE
```

Почему так, а не куча — `docs/adr/0002-static-arena.md`.

## Чего в `render` делать нельзя

- **Блокировать.** Ни `delay`, ни ожидания сети. Бюджет кадра — 16 мс.
- **Выделять память.** Ни `new`, ни `String`, ни `std::vector`.
- **Трогать сеть, базу и ленту.** Ни MQTT, ни `FastLED.show()` — этим занимается конвейер.
- **Думать о яркости и токе.** Рисуй в полную силу: гамма-коррекция и ограничение тока
  применяются к готовому кадру.
- **Использовать Arduino API.** Ни `millis()`, ни `Serial`, ни `random()` — у ядра есть
  своё время (`dtMs`) и `random8()` из FastLED. Это условие делает эффект тестируемым
  на хосте.

## Что доступно из FastLED

Вся цветовая математика: `CRGB`, `CHSV`, палитры (`HeatColor`, `ColorFromPalette`,
`LavaColors_p`), шум (`inoise8`, `inoise16`), `random8`, `qadd8`, `qsub8`, `blend`,
`fadeToBlackBy`, `nscale8`. Это ровно тот инструментарий, из которого собираются
красивые эффекты в двадцать строк.

## Как смотреть, не заливая на плату

Ядро и эффекты не зависят от Arduino, поэтому тот же `Fire.cpp` собирается на компьютере
и крутится в симуляторе:

```bash
pio run -e sim
.pio/build/sim/program --serve      # http://localhost:8266
```

В браузере — матрица 16×16, выбор эффекта, яркость и слайдеры параметров, сгенерированные
из тех же `Param`-объявлений, что и в панели лампы. Сборка занимает секунды: поправил
`render`, пересобрал, перезапустил, обновил страницу.

Тот же симулятор рисует прямо в терминале, если браузер не нужен:

```bash
.pio/build/sim/program --tty          # первый эффект из реестра
.pio/build/sim/program --tty Огонь    # по имени
```

Чего симулятор **не** показывает: ограничение тока (у него нет блока питания), реальную
скорость платы и цветопередачу WS2812B — на ленте красный заметно ярче, чем на мониторе.
Форму, динамику и диапазоны параметров он показывает честно, а это большая часть работы
над эффектом.

## Как проверить

```bash
pio test -e native          # тесты ядра на хосте
pio run -e esp32s3          # сборка под лампу A
pio run -e d1_mini          # сборка под лампу B
```

Эффект компилируется в обе цели автоматически. Если он использует что-то, чего нет на
ESP8266, сборка `d1_mini` это покажет.
